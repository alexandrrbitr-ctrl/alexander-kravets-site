# «Формула роста» — preflight перед коммерческим запуском

**Исходная ветка:** `feature-calculator-discovery` на 18 октября 2026, коммит `c9773be229118e97a6aca3e398e822bae79b16a0`.

**Цель:** автоматизировать проверку SEO/маршрутов перед рассмотрением объединения с `main`. Пакет не объединяет ветки, не публикует сайт, не добавляет внешние счетчики и не собирает данные посетителей.

## Уже установлено в GitHub (повторно применять не нужно)

- Реквизиты ИП в 59 HTML-файлах (в том числе 404, cookies и юридические страницы).
- Пять графиков кейсов, бесплатный калькулятор и страницы `/tools/` и `/tools/sales-economics/`.
- Видимые переходы к калькулятору на главной и странице услуг.
- Отчеты предыдущих браузерных тестов и тестов расчетной модели находятся в `docs/case-calculator-review/` и `docs/ip-footer-review/`.

## Проведённый статический аудит (через GitHub)

- 59 HTML-страниц; 56 индексируемых URL в sitemap; 404, cookies и политика конфиденциальности намеренно не входят в индексируемые.
- На всех 56 индексируемых страницах обнаружено по одному H1, каноническому URL и meta description. Необъясненных `noindex` не найдено.
- `robots.txt` содержит `Allow: /` и путь к sitemap; пустые ID аналитики подтверждены в `analytics-config.js`.
- `CNAME` в дереве ветки отсутствует. Настройка домена `formularosta.eu.org` не подтверждена.
- Ветви `main` и `feature-calculator-discovery` различаются: изменения пока не опубликованы.

**Важный SEO-нюанс:** на GitHub Pages *project site* текущий `robots.txt` находится по адресу `/alexander-kravets-site/robots.txt`. Это не корень хоста `https://alexandrrbitr-ctrl.github.io/robots.txt`, поэтому поисковые роботы не обязаны использовать его при обработке файла robots.txt. sitemap.xml при этом можно предоставить через поисковые кабинеты. После появления подтвержденного собственного домена следует проверить canonical, sitemap, CNAME и robots.txt как один переход, а не менять абсолютные URL заранее.

**Ограничение проверки:** доступность страницы в открытом интернете и фактическая индексация через подключенные кабинеты не подтверждены. Не путать наличие HTML в GitHub с появлением сайта в поиске.

## Что добавляется этим пакетом

- `scripts/check-site.mjs`: статическая проверка всех HTML-страниц, H1, canonical, description, noindex, sitemap, JSON-LD, реквизитов ИП, связанных внутренних ресурсов, ссылок на калькулятор.
- `tests/test-preflight.mjs`: 22 автотеста самого статического аудитора (пять исходных сценариев и регрессионные проверки доработок).
- `scripts/check-live.mjs`: **ручной** проверочный прогон по публичному сайту *после* разрешенного опубликования, без логинов и данных пользователей.
- `.github/workflows/site-preflight.yml`: GitHub Actions для PR в `main` и ручного запуска, только тесты, **без публикации**.
- `docs/release-preflight/README.md`: фиксирует границы проверок и подготовку индексации.

Для проверки в репозитории:

```
node scripts/check-site.mjs
node tests/test-preflight.mjs
node docs/case-calculator-review/test-engine.mjs
node --check site.js
node --check tools/sales-economics/engine.mjs
node --check tools/sales-economics/ui.mjs
```

После публикации (но не до неё):

```
node scripts/check-live.mjs https://alexandrrbitr-ctrl.github.io/alexander-kravets-site/
```

## Подготовка поисковых кабинетов после выбора финального адреса

1. Удостовериться, что домен / адрес и страницы доступны с HTTP 200, не переадресовывают на ошибочный URL.
2. В Google Search Console создать **ресурс с префиксом URL** `https://alexandrrbitr-ctrl.github.io/alexander-kravets-site/` (или финальный домен), подтвердить право. HTML-проверку добавлять только из реального токена Google.
3. Отправить `https://alexandrrbitr-ctrl.github.io/alexander-kravets-site/sitemap.xml` через раздел Sitemap. При переносе на свой домен использовать sitemap и canonical нового домена.
4. В Яндекс Вебмастере использовать **подтвержденный собственный домен**, если это потребуется сервису: Яндекс отдельно предупреждает, что добавляемому сайту нужен свой домен. Отправить sitemap через интерфейс.
5. Включать счетчики/цели только после выдачи реальных ID и проверки политики согласия. Калькулятор не должен посылать пользовательские финансовые вводы в аналитику.

**Не нужно сейчас:** генерировать токены верификации, создавать фиктивный CNAME, менять canonical на домен без подтвержденного подключения или менять `main`.


## Фактический прогон в feature-site-preflight

Пакет применён от `feature-calculator-discovery` / `c9773be229118e97a6aca3e398e822bae79b16a0`. Найдено и устранено ложное срабатывание аудитора для старого `cookies.html`: правильный canonical на политику сохраняется, проверяются оба механизма перехода и существование раздела `#cookies`. Добавлены проверки кратности метаданных, якорей и повторяющихся ID; определение базы больше не зависит от порядка sitemap, некорректная база выдаёт диагностическую ошибку.

Существующие HTML, стили, контакты, кейсы, формулы и интерфейс калькулятора не изменены. [Итоговый отчёт и фактические результаты](REPORT.md).

Браузерные проверки предыдущих веток не повторялись. `check-live.mjs` здесь не запускался: эта ветка не опубликована. Доступ к поисковым кабинетам и подключение собственного домена в данном этапе не проверялись. Наличие файлов в ветке не подтверждает их публикацию или индексацию.

Ограничения аудитора: он проверяет статические HTML-метаданные и ссылки, а не полную HTML-валидность, JSON-LD по правилам rich results, HTTP-ответы, отрисовку или состояние поисковых индексов. Дополнительная проверка XML текущего sitemap выполнена стандартным XML-парсером при локальном прогоне; сам Node-аудитор проверяет набор URL, а не полную XML-схему.
